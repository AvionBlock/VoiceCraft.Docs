# 托管注意事项

不同的提供商和部署风格会影响 VoiceCraft 拓扑的实际情况。

在选择拓扑之前，请确认两条网络路径：

1. 玩家可以到达 VoiceCraft UDP 端点
2. Minecraft 端运行时可以到达选定的传输端点

许多托管问题都源于其中一条路径被阻止，而另一条路径仍然有效。

## 基岩主机

`McHttp` 通常是最好的 Bedrock 传输，但前提是 BDS 节点可以到达 VoiceCraft 端点。

常见的拦截器：

- 出站 HTTP 限制
- 缺少模块权限
- 脚本支持受到限制的世界

如果提供程序阻止出站 HTTP 或所需的脚本模块，则 `McHttp` 在技术上可能是正确的，但在操作上不可用。

## 共享托管提供商

一些提供商不允许：

- 自定义监听器
- 来自游戏服务器的出站 HTTP
- 额外的 sidecar 进程

在这些环境中，技术上支持的拓扑在操作上可能仍然受阻。

具体询问提供商有关游戏服务器的出站 HTTP/TCP 和其他 sidecar 进程的信息。通用的“允许插件”答案是不够的。

## 类似 Aternos 的限制

在严格限制的托管中，HTTP 样式的通信可能会被阻止或不切实际。

当这种情况发生时：

- 基岩 BDS + `McHttp` 可能不可行
- 本地世界或客户端替代方案可能是唯一的路径

不要假设免费/受限主机可以运行与 VPS 或专用计算机相同的拓扑。

## Docker 和容器注意事项

容器有助于隔离，但您仍然需要：

- 港口出版
- 稳定的卷安装配置
- 正确的跨容器网络
- VoiceCraft 客户端端点的显式 UDP 发布
- 托管运行时目录的持久存储

## 反向代理

VoiceCraft 传输并不都是反向代理形状的：

- `McHttp` 可以更自然地适应 HTTP 工具
- `McTcp` 是原始 TCP
- `McWss` 的行为与普通 HTTP 不同

不要假设一种入口策略适用于所有这些策略。

HTTP 工具可以帮助处理 `McHttp`，但它不会自动解决原始 `McTcp` 或客户端 UDP 流量。

## Java 网络注意事项

对于 `GeyserVoice` 代理部署：

- 代理必须可靠地到达 VoiceCraft
- 后端Paper节点必须可靠到达代理消息路径
- 所有权模式必须保持清晰

如果代理不能干净地拥有网桥，拓扑就会变得脆弱。

## 实用的供应商清单

询问或验证：

- 玩家可以访问自定义 UDP 端口吗？
- 游戏服务器可以发出出站 HTTP 请求吗？
- 游戏服务器可以打开或连接到原始 TCP 端口吗？
- 我可以为 `VoiceCraft.Server` 运行 sidecar 进程吗？
- 我可以坚持`config/ServerProperties.json`吗？
- 我可以安装或更新基岩行为/资源包吗？
- 对于Java网络，插件消息能否在后端和代理之间可靠地传递？

如果答案是否定的，请选择避免该要求的拓扑，或将 VoiceCraft 移至您控制的基础设施。
