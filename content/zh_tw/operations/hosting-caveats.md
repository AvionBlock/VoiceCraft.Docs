# 託管注意事項

不同的供應商和部署風格會影響 VoiceCraft 拓撲的實際情況。

在選擇拓撲之前，請確認兩條網路路徑：

1. 玩家可以到達 VoiceCraft UDP 端點
2. Minecraft 端運行時可以到達選定的傳輸端點

許多託管問題都源自於其中一條路徑被阻止，而另一條路徑仍然有效。

## Bedrock主機

`McHttp` 通常是最好的 Bedrock 傳輸，但前提是 BDS 節點可以到達 VoiceCraft 端點。

常見的攔截器：

- 出站 HTTP 限制
- 缺少模組權限
- 腳本支援受到限制的世界

如果提供者阻止出站 HTTP 或所需的腳本模組，則 `McHttp` 在技術上可能是正確的，但在操作上不可用。

## 共享託管提供者

有些提供者不允許：

- 自訂監聽器
- 來自遊戲伺服器的出站 HTTP
- 額外的 sidecar 進程

在這些環境中，技術上支援的拓撲在操作上可能仍然受阻。

具體詢問提供者有關遊戲伺服器的出站 HTTP/TCP 和其他 sidecar 進程的資訊。通用的「允許插件」答案是不夠的。

## 類似 Aternos 的限制

在嚴格限制的託管中，HTTP 樣式的通訊可能會被阻止或不切實際。

當這種情況發生時：

- Bedrock BDS + `McHttp` 可能不可行
- 本地世界或客戶端替代方案可能是唯一的路徑

不要假設免費/受限主機可以運行與 VPS 或專用電腦相同的拓撲。

## Docker 和容器注意事項

容器有助於隔離，但您仍然需要：

- 港口出版
- 穩定的捲安裝配置
- 正確的跨容器網絡
- VoiceCraft 用戶端端點的明確 UDP 發布
- 託管運行時目錄的持久存儲

## 反向代理

VoiceCraft 傳輸並非全是反向代理形狀的：

- `McHttp` 可以更自然地適應 HTTP 工具
- `McTcp` 是原始 TCP
- `McWss` 的行為與一般 HTTP 不同

不要假設一種入口策略適用於所有這些策略。

HTTP 工具可以協助處理 `McHttp`，但它不會自動解決原始 `McTcp` 或客戶端 UDP 流量。

## Java 網路注意事項

對於 `GeyserVoice` 代理部署：

- 代理必須可靠地到達 VoiceCraft
- 後端Paper節點必須可靠地到達代理訊息路徑
- 所有權模式必須保持清晰

如果代理商不能乾淨地擁有網橋，拓樸就會變得脆弱。

## 實用的供應商清單

詢問或驗證：

- 玩家可以存取自訂 UDP 連接埠嗎？
- 遊戲伺服器可以發出出站 HTTP 請求嗎？
- 遊戲伺服器可以開啟或連接到原始 TCP 連接埠嗎？
- 我可以為 `VoiceCraft.Server` 運行 sidecar 進程嗎？
- 可以堅持`config/ServerProperties.json`嗎？
- 我可以安裝或更新 Bedrock 行為/資源包嗎？
- 對於Java網絡，插件訊息能否在後端和代理之間可靠地傳遞？

如果答案是否定的，請選擇避免該要求的拓撲，或將 VoiceCraft 移至您控制的基礎設施。
